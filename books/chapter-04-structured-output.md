# 第4章 Structured Output

## 本章摘要

### 新概念

- **Structured Output**：让模型按固定格式回答，方便程序继续处理。
- **JSON**：一种常见的数据格式，适合把回答拆成字段和值。
- **Schema**：输出结构的说明书，告诉模型和程序应该有哪些字段。
- **结果校验**：程序检查模型有没有按约定输出，发现问题就及时拦住。

### 产品功能增量

- 本章会把 TravelPlanAgent 升级到 v0.3。它的回答不只给人读，也能被程序解析、检查和继续使用。


## 对 TravelPlanAgent 来说意味着什么

到了 v0.2，TravelPlanAgent 已经更像旅行规划助手了。它知道自己的角色，也知道缺少关键信息时应该追问。

但还有一个很实际的问题：模型回答得再自然，程序未必读得懂。

比如用户说：

```text
我想去成都玩三天，预算不高，喜欢小吃。
```

模型可以写出一段很流畅的建议。可如果程序接下来想判断“目的地是什么”“天数是多少”“还缺不缺出行日期”，一整段自然语言就不太方便了。

所以第 4 章会让 TravelPlanAgent 进入 v0.3：

```text
固定输出格式，让模型回答更容易被程序读取
```

这一章我们要做的事很像给模型一张表格：哪些字段必须有，字段里应该写什么，写错了程序怎样发现。这样一来，模型的回答就不只是给人看的文字，也能成为程序下一步处理的数据。


## 本章目标

读完本章，你应该能理解：

1. 为什么 Agent 开发里需要结构化输出。
2. 自然语言输出和结构化输出的差异。
3. JSON、表格、固定字段等常见输出格式各自适合什么场景。
4. 如何通过 Prompt 约束模型输出格式。
5. 为什么结构化输出需要校验，而不能只相信模型“看起来写对了”。

## 为什么自然语言不够

自然语言适合给人看，但不一定适合给程序用。

比如用户问：

```text
帮我安排一个上海两日游，喜欢城市漫步和咖啡馆。
```

模型可能回答：

```text
第一天可以从武康路开始，慢慢走到安福路，下午找一家咖啡馆休息，晚上可以去外滩看看夜景。第二天建议去愚园路和静安寺附近，节奏轻松一点。
```

这段回答读起来没问题。但如果程序想知道：

- 一共有几天？
- 每天有哪些时间段？
- 每个地点叫什么？
- 哪些活动适合下雨天？
- 哪些活动需要预约？
- 每天大概有几个主要地点？

它就要从自然语言里再“猜”一次。

对人来说，这只是阅读理解；对程序来说，这就是不稳定解析。

结构化输出的思路是：既然后续程序要用，那就一开始让模型按程序容易理解的格式输出。

## 什么是 Structured Output

Structured Output 可以翻译成“结构化输出”。

它指的是让模型按照某种明确结构返回结果，而不是自由发挥一大段文字。

常见形式包括：

- JSON
- Markdown 表格
- 固定标题层级
- 固定字段列表
- XML
- 函数调用参数

在 Agent 开发中，最常见也最实用的是 JSON。因为 JSON 很容易被程序读取，也能表达数组、对象、字符串、数字、布尔值等结构。

例如，一个两日游计划可以输出成这样：

```json
{
  "destination": "上海",
  "days": [
    {
      "day": 1,
      "theme": "城市漫步与咖啡馆",
      "schedule": [
        {
          "time": "上午",
          "place": "武康路",
          "activity": "城市漫步，观察街区建筑"
        },
        {
          "time": "下午",
          "place": "安福路",
          "activity": "逛小店并选择咖啡馆休息"
        },
        {
          "time": "晚上",
          "place": "外滩",
          "activity": "看夜景"
        }
      ]
    }
  ]
}
```

这份输出虽然没有自然语言那么随意，但程序更容易处理。

比如我们可以读取 `days` 数组，逐天渲染行程；也可以统计每天 `schedule` 里有几个地点，判断行程是不是太满。

## 什么时候需要结构化输出

不是所有回答都要结构化。

如果用户只是问：

```text
第一次去杭州，有什么整体建议？
```

一段自然语言回答可能就很好。

但只要后续需要程序继续处理，结构化输出就会变得很有价值。

| 场景 | 推荐输出方式 | 原因 |
| --- | --- | --- |
| 给用户解释概念 | 自然语言 | 更亲切，阅读负担低 |
| 展示多天行程 | Markdown 表格或 JSON | 结构清晰，便于比较 |
| 生成可保存的旅行计划 | JSON | 方便存储、读取、修改 |
| 让模型选择工具参数 | JSON 或函数参数 | 程序需要准确读取字段 |
| 批量抽取信息 | JSON 数组 | 方便后续统计和处理 |
| 前端页面渲染 | JSON | 可直接映射到卡片、列表、时间线 |

对 TravelPlanAgent 来说，结构化输出会越来越重要。

早期它可以直接用自然语言回答。后面当我们希望它规划多日行程、调用工具、检查路线合理性时，就需要把结果变成更明确的数据。

## 用 Prompt 约束输出格式

最基础的方式，是在 Prompt 里明确告诉模型输出格式。

例如：

```text
请根据用户需求输出旅行计划。
要求只输出 JSON，不要输出额外解释。

JSON 字段：
- destination：目的地，字符串
- duration_days：旅行天数，数字
- preferences：用户偏好，字符串数组
- itinerary：行程数组，每一项包含 day、time、place、activity
```

这比简单说“输出 JSON”更好，因为它告诉了模型字段名和字段含义。

如果再给一个示例，稳定性会更好：
```json

{
  "destination": "杭州",
  "duration_days": 2,
  "preferences": ["自然风景", "轻松"],
  "itinerary": [
    {
      "day": 1,
      "time": "上午",
      "place": "西湖",
      "activity": "沿湖散步"
    }
  ]
}
```

这其实就是第 3 章的 Few-shot 思路在结构化输出中的应用。

## 结构化输出不等于一定正确

这里要特别小心：模型输出了 JSON，不代表内容一定正确。

它可能出现两类问题。

第一类是格式问题：

- 少了逗号；
- 多了注释；
- 字符串没有加引号；
- 输出了 JSON 外的解释文字；
- 字段名不一致。

第二类是内容问题：

- 把天数理解错；
- 编造实时票价；
- 行程安排过满；
- 用户说不想太累，但输出一天八个景点；
- 字段格式对了，但内容不符合需求。

所以结构化输出通常要配合校验。

程序可以检查：

- JSON 是否能被解析；
- 必填字段是否存在；
- 字段类型是否正确；
- 数组是否为空；
- 天数是否和用户需求一致；
- 是否出现不允许的内容。

结构化输出不能保证模型永远不犯错，但能让程序更容易发现错误。

## Schema：给输出一份更严格的说明书

当结构变复杂时，只用自然语言描述字段可能不够。这时我们会使用 Schema。

Schema 可以理解为“数据应该长什么样的说明书”。

例如我们希望 TravelPlanAgent 输出旅行计划，可以描述成：

```text
TravelPlan:
- destination: string
- duration_days: integer
- preferences: list[string]
- itinerary: list[DayPlan]

DayPlan:
- day: integer
- theme: string
- schedule: list[ScheduleItem]

ScheduleItem:
- time: string
- place: string
- activity: string
- indoor: boolean
```

这段内容还不是具体代码，它先告诉模型和程序：输出应该有哪些字段，每个字段是什么类型。

后面使用 Pydantic AI 等框架时，Schema 会变得更具体。我们可以用 Python 类型或 Pydantic Model 来定义输出结构，让框架帮我们校验结果。

现在先记住：

> Prompt 负责告诉模型怎么输出，Schema 负责让程序知道如何检查输出。

## Markdown 表格也是一种结构化输出

结构化输出不一定非要 JSON。

如果目标主要是给人看，Markdown 表格有时更合适。

例如：

| 时间 | 地点 | 安排 | 备注 |
| --- | --- | --- | --- |
| 上午 | 西湖 | 沿湖散步 | 节奏轻松 |
| 下午 | 灵隐寺 | 参观寺院 | 注意预约 |
| 晚上 | 河坊街 | 吃小吃 | 避开太晚 |


表格的好处是阅读友好，适合教材、报告或聊天回复。

但如果程序要继续处理每个字段，JSON 通常更稳。

所以可以这样选择：

- 给人看：Markdown 表格、分点列表。
- 给程序用：JSON、函数参数、Schema。
- 两者都要：内部用 JSON，展示时再渲染成人类友好的格式。

## 小结

这一章解决的是一个很实际的问题：模型回答得再漂亮，程序也未必好处理。

所以我们给输出加上结构：

- 自然语言适合给人读，结构化输出更适合给程序读；
- JSON 是 Agent 开发里很常见的结构化格式；
- Markdown 表格适合展示，JSON 更适合继续处理；
- Prompt 和 Few-shot 可以帮助模型按格式输出；
- Schema 和校验可以帮助程序发现格式错误或缺字段。

到这里，第一部分的准备就差不多了。TravelPlanAgent 已经能调用模型，也开始有角色、有输出约束。接下来我们会进入更像 Agent 的部分：上下文、工具和行动循环。
