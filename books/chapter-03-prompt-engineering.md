# 第3章 Prompt Engineering

## 本章摘要

### 新概念

- **Prompt Engineering**：把任务、角色、限制和例子说清楚，让模型少靠猜。
- **System Prompt**：写给模型的长期说明，像给助手的一份岗位说明书。
- **User Prompt**：用户这一轮真正要做的事，决定模型当下处理什么。
- **Zero-shot / Few-shot**：前者直接做，后者先给几个样例再让模型照着做。

### 产品功能增量

- 本章会把 TravelPlanAgent 推到 v0.2。它开始知道自己是旅行规划助手，也开始学会在信息不够时追问。


## 对 TravelPlanAgent 来说意味着什么

现在 TravelPlanAgent v0.1 已经能调用 LLM 了。但你很快会发现，能调用模型只是一回事，模型回得像不像一个旅行规划助手，是另一回事。

如果我们只是把用户问题原样转给模型，它可能回答得不错，也可能忽然变得啰嗦、跑题，或者在不知道实时信息时说得很自信。这样的程序能聊天，但还不像一个可靠的助手。

第 3 章会把它推到 v0.2：

```text
优化 System Prompt 和 User Prompt，让它更像旅行规划助手
```

从这里开始，我们要给这个小助手写“工作说明”：它是谁，能做什么，遇到不确定信息怎么办，缺少旅行日期、预算、偏好时要不要追问。

Prompt Engineering 在这里不用先想得很神秘。你可以把它看成一件普通的事：把任务交代清楚。只是这次听你交代任务的对象，是一个会根据上下文生成内容的模型。


## 本章目标

读完本章，你应该能理解：

1. Prompt Engineering 关注任务说明、上下文和约束设计，不靠“咒语感”取胜。
2. 一个基础 Prompt 通常包含 System、User、Tool 等不同来源的信息。
3. Zero-shot 和 Few-shot 分别适合什么情况。
4. 如何让 TravelPlanAgent 的回答更像一个稳定的助手，而不是随口聊天。

## Prompt 到底是什么

如果你只是在聊天框里问：

```text
帮我规划一个北京三日游。
```

这当然也是 Prompt。

但在 Agent 开发里，我们通常不会只把用户这一句话原样丢给模型。因为模型并不知道：

- 它应该扮演什么角色；
- 回答要详细到什么程度；
- 是否可以编造不确定的信息；
- 输出要不要有固定格式；
- 遇到信息不足时要不要追问；
- 是否可以调用工具；
- 工具结果应该怎样被使用。

一个更完整的 Prompt，通常不是孤零零一句问题，而是一组经过组织的信息。

它可能包含：

- System：给模型的长期规则和角色设定；
- User：用户当前提出的需求；
- Assistant：历史回复；
- Tool：工具返回的观察结果；
- Developer 或平台规则：课程、产品或系统层面的约束。

我们在第 2 章见过 `messages`。Prompt Engineering 的很多工作，本质上就是认真设计这些 messages 里应该放什么、怎么放、放到什么程度。

## Prompt 要像分配任务一样清楚

很多初学者写 Prompt 时，会下意识写成一种愿望：

```text
请给我一个好的旅行计划。
```

这句话不是错，但它留给模型的自由度太大了。

“好”到底是什么标准？预算低算不算好？景点多算不算好？轻松算不算好？适合亲子算不算好？如果模型不知道你的判断标准，它只能自己猜。

更好的 Prompt 像是在分配一个清楚的任务：

```text
你是一个旅行规划助手。
请为第一次去杭州的用户规划一个两天一夜行程。
用户偏好：轻松、不赶路、喜欢自然风景和本地小吃。
要求：
1. 每天最多安排 3 个主要地点。
2. 按“上午 / 下午 / 晚上”分段。
3. 对不确定的实时信息不要编造。
4. 如果缺少出发地、预算或出行日期，请先提醒用户补充。
```

这段 Prompt 可能不够完美，但它比“给我一个好的旅行计划”稳定得多。

因为它告诉模型：

- 你是谁；
- 任务是什么；
- 用户偏好是什么；
- 输出结构是什么；
- 哪些事情不能做；
- 信息不足时怎么办。

Agent 开发里，很多所谓“模型不听话”的问题，其实是任务没有讲清楚。

## Prompt 的基础结构

本课程里，我们先把 Prompt 的基础结构拆成三块来看：

- System：角色和规则。
- User：用户需求。
- Tool：外部世界返回的信息。

### System：给 Agent 定性格和边界

`system` 消息通常写的是长期规则。

例如 TravelPlanAgent 可以有这样的 system prompt：

```text
你是 TravelPlanAgent，一个专业、耐心、诚实的旅行规划助手。

你的目标是帮助用户制定可执行的旅行计划。

你需要遵守以下规则：
1. 不编造实时天气、票价、营业时间等可能变化的信息。
2. 如果缺少关键条件，先提出简短追问。
3. 回答要清晰、分点，不要堆砌景点名称。
4. 优先考虑用户预算、体力和兴趣偏好。
```

这段内容不会每一轮都由用户输入，而是由程序放进 `messages`。它像是 TravelPlanAgent 的“工作守则”。

好的 system prompt 不需要写得很玄。它应该具体、可执行、能影响模型行为。

### User：表达用户当前需求

`user` 消息是用户真正说的话。

例如：

```text
我想去成都玩三天，预算不高，喜欢吃小吃，不想太赶。
```

这句话里已经包含了不少信息：

- 目的地：成都；
- 时长：三天；
- 预算：不高；
- 兴趣：小吃；
- 节奏：不想太赶。

TravelPlanAgent 要做的不是机械回答，而是识别这些条件，并把它们转化成规划约束。

如果用户只说：

```text
帮我安排一下旅行。
```

那就缺少目的地、时间、预算、偏好等关键信息。一个好的 Agent 不应该硬编，而应该先追问。

### Tool：让模型使用真实信息

工具结果不是用户说的话，也不是模型自己想出来的内容，而是外部系统返回的信息。

比如后面我们给 TravelPlanAgent 增加天气工具后，工具可能返回：

```text
成都未来三天有小雨，气温 18 到 24 摄氏度。
```

这段信息应该作为 Tool 或 Observation 一类内容交给模型。模型再根据它调整建议，比如提醒带伞、减少户外长时间步行、把博物馆或室内美食街作为备选。

这里要先记住一个原则：

> 工具结果是事实输入，模型回答是基于事实输入的组织和表达。

如果模型没有工具结果，却说“明天成都一定晴天”，那就属于不可靠回答。Prompt 里要提前约束：不要编造实时信息。

## Zero-shot：不给示例，直接让模型完成任务

Zero-shot 指的是不给模型示例，直接描述任务，让模型完成。

例如：

```text
你是旅行规划助手。
请根据用户需求规划一个两天一夜杭州行程。
要求按“上午 / 下午 / 晚上”输出。
用户需求：第一次去杭州，喜欢自然风景，不想太赶。
```

这里没有给模型“标准答案示例”，只给任务和约束。这就是 Zero-shot。

Zero-shot 的优点是简单、灵活、成本低。很多常见任务都可以先从 Zero-shot 开始。

适合 Zero-shot 的情况：

- 任务比较常见；
- 输出格式不复杂；
- 对风格稳定性要求不高；
- 你还在探索模型大概能做到什么程度。

比如让模型解释一个概念、总结一段文字、给出普通旅行建议，Zero-shot 往往已经够用。

## Few-shot：给几个示例，让模型照着做

Few-shot 指的是在 Prompt 里给模型几个输入输出示例，再让它处理新输入。

例如我们希望 TravelPlanAgent 遇到信息不足时，不要直接乱规划，而是提出追问。可以给它示例：

```text
示例 1：
用户：帮我安排一次旅行。
助手：可以，我需要先了解目的地、出行天数、预算和偏好，才能给你更合适的计划。

示例 2：
用户：我想去北京玩三天，喜欢历史文化，预算中等。
助手：好的，我可以按历史文化路线为你安排北京三日游，并控制行程节奏。

现在请处理新的用户输入：
用户：我想出去玩，不想太累。
```

模型看到示例后，更容易理解我们希望它怎么判断“信息是否足够”，以及应该用什么语气追问。

Few-shot 的优点是能提升格式和风格稳定性。它特别适合：

- 输出格式比较固定；
- 判断标准不容易一句话说清；
- 希望模型模仿某种语气；
- 希望模型处理边界情况。

但 Few-shot 也不是越多越好。示例太多会占用上下文，还可能让模型被某些示例带偏。

## 好 Prompt 的几个判断标准

我们可以用一个简单清单来检查 Prompt：

| 检查项 | 问自己一个问题 |
| --- | --- |
| 角色是否清楚 | 模型知道自己现在是谁吗？ |
| 任务是否具体 | 模型知道要完成什么，而不是只知道大方向吗？ |
| 约束是否可执行 | 要求是否能被模型实际遵守？ |
| 输入是否完整 | 用户需求、历史信息、工具结果是否放对位置？ |
| 输出是否明确 | 模型知道用什么格式、详细到什么程度吗？ |
| 失败策略是否存在 | 信息不足、事实不确定时应该怎么办？ |

好的 Prompt 不一定很长，但一定要减少模型“自己猜”的空间。

## 小结

这一章我们做的事，其实就是把“怎么跟模型交代任务”讲清楚。

你可以先这样记：

- System Prompt 像长期工作说明，决定 Agent 的身份和边界；
- User Prompt 是用户这一轮真正要处理的需求；
- Tool 信息不能混成用户说的话，要清楚标出来源；
- Zero-shot 适合简单任务；
- Few-shot 适合需要稳定格式、风格或判断标准的任务。

下一章会继续往前走：如果不仅希望模型说得清楚，还希望程序能稳定读取模型回答，就需要 Structured Output。
