# 第5章 Agent 概述


到目前为止，我们已经让程序能够调用 LLM，也学会了通过 Prompt 和 Structured Output 让模型回答得更像一个旅行规划助手。

但这里有一个值得停下来想一想的问题：

> 只要能够调用 LLM，它就已经是 Agent 了吗？

严格来说，还不能这么简单地下结论。

TravelPlanAgent v0.1 到 v0.3 已经有了一个不错的起点：

- 能接收用户输入；
- 能调用 LLM；
- 能带着角色设定回答；
- 能按照固定格式输出内容。

但它还缺少一些关键能力。比如：

- 用户补充一句“我更喜欢轻松一点”，它能不能记住前面说过什么？
- 用户问“明天上海会下雨吗”，它能不能主动查询真实天气？
- 一个旅行任务需要查天气、找景点、安排路线，它能不能判断下一步该做什么？
- 得到工具结果后，它能不能继续调整计划？

接下来几章，我们会让 TravelPlanAgent 从“包装过的 LLM 对话程序”，逐渐变成一个真正会做事的 Agent。

---

## 本章目标

读完本章，你应该能理解：

1. Agent 和普通 LLM 对话程序有什么区别。
2. 一个 Agent 通常由哪些部分组成。
3. 自主性、反应性、主动性、社交能力、学习能力这些特征分别意味着什么。
4. 为什么 Agent 不等于“模型自由发挥”，而是模型、工具、记忆和流程共同组成的系统。

## 什么是 Agent

Agent一词起源于拉丁语中的Agere，意思是“to do”。在LLM语境下，Agent可以理解为在某种能自主理解、规划决策、执行复杂任务的**智能体**。

这个词听起来有点抽象，但我们可以从一个很朴素的角度理解：

> Agent 是一个能够接收目标、观察环境、选择行动，并根据行动结果继续完成任务的系统。

普通聊天机器人更像是：

```text
用户提问 → 模型回答
```

Agent 更像是：

```text
用户提出目标
→ Agent 判断还缺什么信息
→ 选择合适的行动
→ 调用工具或查询资料
→ 观察结果
→ 继续判断下一步
→ 直到给出最终结果
```

比如用户说：

```text
我周末想去杭州玩两天，帮我安排一个适合雨天的轻松行程。
```

一个普通 LLM 可能直接生成一份看起来不错的行程。

一个更可靠的 Agent 则会意识到：

- “周末”对应哪两天？
- 杭州天气真的会下雨吗？
- 哪些地点适合室内活动？
- 用户说“轻松”，每天应该安排多少地点？
- 如果天气预报变化，是否需要准备备选方案？

它可能先查询天气，再检索旅行知识，最后生成计划。

这就是 Agent 和普通问答程序的差异：**Agent 不只会生成回答，还会为了完成目标采取行动。**

## Agent 通常由哪些部分组成

一个基础 Agent 不一定很复杂，但通常会包含下面这些部分：

| 组成部分 | 作用 | 在 TravelPlanAgent 中的例子 |
| --- | --- | --- |
| 用户目标 | 告诉 Agent 要完成什么 | “帮我规划上海三日游” |
| LLM | 理解需求、生成计划、做判断 | 识别用户偏好，组织最终回复 |
| Prompt | 规定 Agent 的角色和行为边界 | 不编造实时天气，信息不足时先追问 |
| Memory | 保存必要的历史信息 | 记住用户预算低、喜欢小吃 |
| Tools | 获取外部真实信息或执行动作 | 查询天气、搜索攻略、读取本地知识 |
| Observation | 工具执行后返回的结果 | 上海当前有雨，建议保留室内备选 |
| Workflow | 规定任务怎样一步步推进 | 先查天气，再找景点，再安排行程 |

并不是每个 Agent 都必须一次性拥有所有部分。

本课程会采用“小步迭代”的方式逐渐加入这些能力。你会看到 TravelPlanAgent 每次只多长出一块：

1. 先能调用 LLM；
2. 再学会使用 Prompt；
3. 再固定输出格式；
4. 再增加上下文记忆；
5. 再加入工具；
6. 再形成 Think-Act-Observe 循环；
7. 再加入 RAG；
8. 最后学习任务规划和 Multi-Agent。

这样学习的好处是：每次代码变化都不会太大，你能清楚知道“这一章到底新增了什么”。

## Agent 的五个核心特征

一个合格的 AI Agent 通常具备五个核心特征：

| 核心特征 | 一句话理解 | TravelPlanAgent 中的表现 |
| --- | --- | --- |
| 自主性（Autonomy） | 无需用户逐步指导，能够自己决定下一步做什么 | 根据用户目标判断要不要查天气、搜索攻略或读取本地小贴士 |
| 反应性（Reactivity） | 感知环境变化，并根据新信息调整行为 | 天气工具返回阵雨后，主动增加室内备选 |
| 主动性（Proactivity） | 不只被动回答，还会为了目标提前发现问题 | 发现日期、预算不明确时先追问，提醒用户核验预约信息 |
| 社交能力（Social Ability） | 能与人类或其他 Agent 交互协作 | 通过自然语言多轮对话确认偏好，后续还能与子 Agent 配合 |
| 学习能力（Learning） | 从历史交互中保存和使用经验 | 记住用户喜欢慢节奏、小吃和公共交通 |

这些词如果只背定义，会有些生硬。把它们放回 TravelPlanAgent 的设计里，就容易理解很多。

### 自主性（Autonomy）：自己决定下一步做什么

自主性是指 Agent 不需要人类一步一步告诉它每个操作，而是能够围绕目标独立运作。

用户不会这样下指令：

```text
第一步，请判断我的问题是否涉及天气。
第二步，如果涉及天气，请调用天气 API。
第三步，请读取 API 返回结果。
第四步，请根据结果给出建议。
```

真实用户只会说：

```text
我明天去广州，天气适合步行吗？
```

TravelPlanAgent 需要自己判断：这个问题涉及实时天气，仅凭模型已有知识不够可靠，应该调用 `weather_api`。

如果用户换成：

```text
我去杭州玩两天，有什么本地出行提醒？
```

Agent 又可以选择调用 `local_function`，读取本地中保存的小贴士。

这种“**用户只提供目标，Agent 自己选择下一步行动**”的能力，就是自主性。

自主性不等于想做什么就做什么。Agent 仍然只能在系统允许的范围内行动：调用被注册的工具、遵守 Prompt 约束、处理明确的旅行任务。

### 反应性（Reactivity）：环境变化后及时调整

Agent 的行动不是发出去就结束了。

它还需要感知外部环境，并根据新信息调整行为。

例如用户计划在广州进行一天的城市漫步，天气工具返回：

```text
广州当前气温较高，有短时阵雨。
```

TravelPlanAgent 不应该无视结果，继续机械地推荐全天户外步行。它应该做出调整：

- 减少正午长时间户外活动；
- 提醒用户带伞；
- 给行程增加博物馆、商场或茶馆等室内备选；
- 尽量选择地铁方便到达的区域。

如果查询结果发生变化，建议也要跟着变化。

这就是反应性：**先观察环境，再根据环境做出响应。**

### 主动性（Proactivity）：发现问题并提前行动

反应性和主动性很容易混淆。

- 反应性强调：环境已经变化，Agent 及时调整。
- 主动性强调：为了完成目标，Agent 主动发现还缺什么、可能有什么风险。

例如用户说：

```text
帮我安排一次旅行。
```

一个不太可靠的系统可能立刻生成一份随意行程。

一个更好的 TravelPlanAgent 会发现信息不足，并先追问：

```text
你想去哪里？计划玩几天？大概预算是多少？有特别喜欢或不喜欢的活动吗？
```

主动性还可以体现在提醒上。

例如 Agent 发现用户要安排热门景点，就可以提醒：

```text
故宫、国家博物馆等景点通常需要提前预约，建议出行前再次确认开放时间和预约规则。
```

它不是等用户问“要预约吗”才回答，而是为了让旅行计划更可执行，提前指出风险。

### 社交能力（Social Ability）：通过沟通和协作完成任务

社交能力并不是说 Agent 要像真人一样闲聊，而是说它能够与人类或其他 Agent 进行有效交互。

旅行规划通常不是一句话就能完成。用户可能先说目的地，再补充预算，再说同行人有老人，最后又希望增加美食体验。

TravelPlanAgent 需要通过多轮沟通逐步澄清需求：

```text
用户：我想去成都玩三天。
Agent：你更喜欢美食、文化还是自然风景？预算大概是多少？
用户：预算不高，主要想吃小吃，不想太赶。
Agent：明白了，我会按慢节奏美食路线规划。
```

下一章我们就会实现这项基础能力：让 TravelPlanAgent 记住最近 5 轮对话。

在更后面的 Multi-Agent 版本中，社交能力还会体现在 Agent 之间的协作上。例如主 Agent 可以把“查询天气”“检索景点”“安排行程”分配给不同子 Agent，再汇总结果。

### 学习能力（Learning）：从历史交互中积累经验

“学习”这个词很容易被说得过于神奇。

对很多入门 Agent 来说，学习并不意味着模型立刻重新训练。更常见的做法是保存并使用历史信息：

- 保存用户偏好；
- 保存最近对话；
- 记录工具调用结果；
- 从知识库检索资料；
- 根据反馈调整后续回答。

例如用户曾经说：

```text
我不喜欢太赶的行程，更喜欢街区散步和小店。
```

如果 TravelPlanAgent 后续能够使用这段偏好，它就可以少问一次问题，也不容易推荐一天跑八个景点的行程。

再比如用户经常选择：

```text
预算较低、公共交通、早上不要安排太早
```

一个有长期记忆能力的 Agent 可以在后续旅行规划中主动参考这些偏好。

第 6 章会先实现短期上下文记忆，第 12 章会进一步讲长期 Memory。现在先记住：

> Agent 的学习能力，往往从“保存信息，并在合适的时候重新使用”开始。

## Agent 不是让 LLM 无限自由发挥

有些人第一次接触 Agent，会觉得 Agent 就是“让模型自己想办法做事”。

这只说对了一半。

一个可用的 Agent 必须有边界。

例如旅行 Agent 可以调用天气工具，但不应该拥有随意修改用户文件的权限；可以搜索景点资料，但不能把搜索结果不加判断地当成绝对事实；可以生成建议，但涉及实时票价和营业时间时应提醒用户再次核验。

Agent 的可靠性来自：

- 可控的工具集合；
- 清楚的 Prompt；
- 必要的输入校验；
- 可观察的工具结果；
- 合理的任务流程；
- 对失败情况的处理。

换句话说：

> Agent 不是把控制权全部交给模型，而是让模型在设计好的系统里做合适的判断。

## Agent 和 Workflow 有什么区别

Workflow 可以理解为固定流程。

例如：

```text
查询天气 → 查询景点 → 生成行程 → 输出结果
```

无论用户问什么，都按这个顺序执行。

Agent 更灵活一些。它会根据问题判断是否需要每一步。

例如：

- 用户只问“成都有什么小吃”，可能不需要查询天气；
- 用户问“上海明天下雨吗”，可能只需要天气工具；
- 用户问“帮我规划杭州三日游”，才需要多个步骤。

| 对比项 | Workflow | Agent |
| --- | --- | --- |
| 流程 | 预先写死 | 根据任务动态选择 |
| 优点 | 稳定、容易测试 | 灵活，适合复杂任务 |
| 风险 | 不够灵活 | 行为更难预测，需要约束 |
| 适合场景 | 固定业务流程 | 需求变化较多、需要判断的任务 |

实际项目中，两者并不是非此即彼。

一个成熟 Agent 经常会把两者结合起来：外层用 Workflow 控制大步骤，步骤内部再让 Agent 做有限选择。

## 小结

这一章我们正式认识了 Agent：

- Agent 不只是调用 LLM，而是能围绕目标观察、判断、行动并继续调整的系统。
- Prompt、Memory、Tools、Observation 和 Workflow 都是 Agent 的重要组成部分。
- Agent 常见特征包括自主性、反应性、主动性、社交能力和学习能力。
- 自主不等于无限自由，而是在清楚边界中选择下一步行动。
- Workflow 和 Agent 可以结合使用，一个负责稳定流程，一个负责灵活判断。

下一章我们会先补上一个非常基础、也非常重要的能力：上下文记忆。

TravelPlanAgent 将从“每一轮都像第一次见面”，升级成“能记住最近聊过什么”。
