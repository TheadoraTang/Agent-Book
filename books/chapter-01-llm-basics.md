# 第1章 LLM 基础

## 本章摘要

### 新概念

- **LLM**：会根据上下文继续生成内容的模型，文字、代码、JSON 都可以是它的输出。
- **Token**：模型读文本时用的小颗粒，可以先把它想成“模型眼里的字块”。
- **Attention**：模型在一段上下文里分配注意力，判断哪些内容更该被看见。
- **Pipeline 与 Agent**：Pipeline 像固定流水线，Agent 则会根据中间结果决定下一步。

### 产品功能增量

- 本章让你先认识 TravelPlanAgent 的“发动机”。后面写代码时，你会知道自己具体在做什么：组织上下文、调用模型、读取输出。


### 对 TravelPlanAgent 来说意味着什么

我们后面会一直改造一个小程序：TravelPlanAgent。

它最开始很普通，只是在命令行里接收一句话，把这句话发给 LLM，再把模型回复打印出来。这个版本看起来简单，但它已经包含了 Agent 开发最底层的一件事：**程序怎样驱动一个大语言模型**。

后面我们会继续给它加能力：让它有固定角色，记住几轮对话，调用天气工具，检索旅行知识库，拆解旅行任务，最后还能用框架重写。听上去很多，不过先别急。所有这些能力，都要从同一个问题开始：

> LLM 到底根据什么生成回答？

这一章先不追数学推导，也不把 Transformer 讲成论文阅读。你只需要先建立一个实用印象：LLM 会看见一段上下文，然后根据这段上下文继续生成内容。以后我们写 TravelPlanAgent，其实就是在认真设计它能看见什么、能调用什么、什么时候该停下来。

在正式写 Agent 之前，我们先看看这个“会续写上下文的模型”到底靠什么工作。


## 本章目标

读完本章，你应该能回答四个问题：

1. LLM 是什么，它为什么能生成自然语言和代码？
2. Transformer 和 Attention 大致解决了什么问题？
3. 利用 LLM 编程，与传统编程最大的思维差异在哪里？
4. 在程序中使用 LLM 时，pipeline 和 agent 有什么区别？

## LLM 是什么

LLM 是 Large Language Model 的缩写，中文通常叫“大语言模型”，是基于大量数据进行预训练的超大型深度学习模型。
底层转换器是一组神经网络，这些神经网络由具有自注意力功能的编码器和解码器组成。编码器和解码器从一系列文本中提取含义，并理解其中的单词和短语之间的关系

一个非常实用的理解方式是：LLM 是一个根据上下文继续生成内容的模型。你给它一段输入，它会根据已经看到的内容，预测接下来最合适出现的内容。

这里的“内容”不只限于中文或英文句子，也可以是：

- Python 代码
- JSON 数据
- Markdown 文档
- SQL 查询
- 错误日志分析
- 行程规划建议
- 工具调用参数
- ........

所以，LLM 当然会“说话”，但它处理的范围比聊天大得多。代码、配置、说明书、聊天记录，都可以作为文本交给它。

![llm-img](assets/llm-context-map.png)

上图里最关键的是“**上下文**”两个字。

LLM 每次生成回答时，都要先看见一段上下文。它会看见你这次请求中提供的内容，包括问题、历史对话、系统要求、工具结果、参考资料等，然后在这些内容的基础上继续生成。

这也是为什么同一个问题，用不同的说法问，答案可能会不一样。因为你改变的不只是“问题文本”，而是改变了模型看到的上下文。

## 它不是数据库，也不是搜索引擎

很多初学者会把 LLM 当成一个“**百事通**”。这会带来一个危险的误解：只要模型说得很自信，就以为它一定知道事实。

更准确地说：

- LLM 擅长根据语言模式组织答案。
- LLM 擅长把零散信息整理成清晰结构。
- LLM 擅长根据示例模仿格式。
- LLM 不保证自己说出的事实一定最新、一定正确。
- LLM 不能自动知道你电脑里的文件、数据库或实时天气，除非你把这些信息提供给它，或者让它调用工具获取。

这就是 Agent 后面要学习 Tool Calling 和 RAG 的原因。

如果 LLM 是大脑，那么工具、知识库、记忆、环境感知就是它连接真实世界的手、眼睛和笔记本。没有这些能力，一个模型再聪明，也只能在你给它的上下文里“想办法”。

## Token：模型看世界的基本颗粒

人读一句话时，会自然看到词语、句子和含义；LLM 处理文本时，会先把文本切分成 token。

token 可以粗略理解为“模型处理文字时的基本小片段”。它可能是一个字、一个词的一部分、一个符号，或者一小段常见字符组合。

例如这句话：

```text
帮我规划三天上海旅行
```

模型不会像人一样完整地“看见一句话”，而是会把它拆成若干 token，再逐步处理这些 token 之间的关系。

我们现在不需要深入 token 的计算细节，只要先记住两件事：

1. 输入越长，token 越多，成本和处理压力越高。
2. 模型一次能看见的 token 数量有限，这个范围叫上下文窗口。

第 6 章会专门讲 Token 与上下文机制。现在先有一个印象就够了：LLM 的“记忆”并不是无限的，我们需要主动管理它能看到什么。

## Transformer：让模型同时观察整段上下文

Transformer 是现代 LLM 背后的核心模型结构。它解决的一个重要问题是：如何让模型在生成内容时，有效理解一整段文本中不同部分之间的关系。

比如这句话：

```text
小明把护照放进背包，因为它明天出国要用。
```

这里的“它”指什么？人读起来知道大概率是“护照”，不是“背包”。模型要做类似判断，就需要在句子内部建立词语之间的关联。

Transformer 中非常重要的机制叫 Attention，中文常译为“注意力机制”。它的直觉很简单：当模型处理某个 token 时，它会判断上下文里哪些 token 更值得关注。

注意，这只是帮助理解的教学动画，不是模型内部真实数值的完整展示。真正的 Attention 会有更多层、更多头、更多矩阵计算。但从学习 Agent 开发的角度，我们现在需要抓住的重点是：

> LLM 生成每一小段内容时，都在参考上下文中与当前生成最相关的部分。

## LLM 为什么能写代码

代码也是语言，只是它的规则更严格。

在训练过程中，模型见过大量代码、注释、文档、错误信息、提交记录和问答内容。于是它学会了很多模式：

- 函数通常怎么定义
- API 通常怎么调用
- 报错通常意味着什么
- 一段需求通常会对应什么代码结构
- 一段测试失败通常该从哪里检查

所以，当你让 LLM 写一个函数时，它不会像编译器那样推导出唯一答案；它会根据上下文，生成一个看起来最合适的版本。

这也是为什么我们和 LLM 协作写代码时，不能只说“写个 Agent”。这句话太空了，模型会自己补很多细节，而它补出来的细节未必是你想要的。

更好的方式是逐步给清楚边界：

- 这个 Agent 的角色是什么？
- 输入是什么？
- 输出格式是什么？
- 可以调用哪些工具？
- 遇到信息不足时怎么办？
- 代码要跑在什么环境里？

Prompt Engineering 的本质，就是把这些边界用模型能理解的方式表达出来。

## 利用 LLM 编程和传统编程的思维差异

传统编程里，我们习惯写下确定的指令。比如：

```text
如果分数大于等于 60，就输出“及格”；否则输出“不及格”。
```

程序会严格按照规则执行。只要输入一样，代码一样，输出就一样。

LLM 协作则更像是“给一个聪明但不总是稳定的助手分配任务”。它能理解意图，能补全细节，也能灵活表达；但它可能误解、遗漏、发散，甚至把不确定的事情说得很像真的。


| 对比项   | 传统编程           | LLM 协作编程               |
| -------- | ------------------ | -------------------------- |
| 核心方式 | 写确定规则         | 设计上下文与约束           |
| 输出特点 | 稳定、可复现       | 灵活、有概率性             |
| 擅长任务 | 精确计算、流程控制 | 文本理解、生成、总结、规划 |
| 常见问题 | 语法错误、逻辑错误 | 幻觉、跑题、格式不稳定     |
| 开发重点 | 算法和数据结构     | Prompt、上下文、工具、验证 |

做 Agent 开发时，这种差异会更加明显。

Agent 会给 LLM 一个可以行动的系统，让它在系统边界内完成任务：

- 它能看到用户输入。
- 它能保存一部分上下文。
- 它能调用外部工具。
- 它能观察工具结果。
- 它能根据结果继续思考。
- 它最终给出用户需要的答案或行动方案。

这就像把一个会说话的大脑，放进一个有手、有眼睛、有工作流程的身体里。

## 程序中使用 LLM 的两种方式：pipeline 与 agent

知道怎样调用 LLM 之后，我们还会遇到一个很实际的问题：

> 程序应该怎样安排 LLM 的工作？

一种常见的理解方式是：在程序中使用 LLM，大致可以分为 **pipeline** 和 **agent** 两种方式。它们都可以调用模型，也都可以连接外部数据，但“谁来决定下一步做什么”并不一样。

### Pipeline：程序提前安排好流程

pipeline 可以翻译为“流水线”。开发者先用代码写好执行顺序，LLM 只是其中的一个处理环节。

例如，一个简单的旅行建议 pipeline 可能是：

```python
weather = get_weather("上海")
guide = search_travel_guide("上海")
prompt = build_prompt(weather, guide)
plan = llm_generate(prompt)
print(plan)
```

它的执行路径非常清楚：

```text
查询天气
→ 搜索攻略
→ 拼接 Prompt
→ 调用 LLM
→ 输出旅行计划
```

无论用户问什么，程序都会按照这条路径运行。模型负责生成内容，但流程控制权仍然在代码手里。

pipeline 的优点是稳定、容易理解、成本相对容易估算。如果一次调用就能准备好所有必要信息，它通常是很合适的选择。

### Agent：让模型参与决定下一步

agent 的思路不同。程序会为 LLM 提供若干工具，让模型根据用户目标和当前信息决定下一步行动。

例如，TravelPlanAgent 可以拥有这些工具：

```text
get_weather
search_travel_guide
query_attractions
```

当用户说：

```text
我周末想去上海散步，如果下雨就推荐室内景点。
```

Agent 可能先查询天气。如果发现会下雨，再查询室内景点；如果天气晴朗，则搜索适合步行的城市漫步路线。

```text
理解用户目标
→ 判断需要查询天气
→ 调用 get_weather
→ 观察天气结果
→ 决定搜索室内景点或步行路线
→ 生成建议
```

这里的关键不是工具数量，而是：

> 模型可以根据中间结果继续决定下一步，而不是完全按照一条预先写死的路径执行。

### 两种方式怎样选择

pipeline 和 agent 没有绝对的高下之分。它们适合不同的问题。

| 判断维度 | 更适合 pipeline | 更适合 agent |
| --- | --- | --- |
| 执行流程 | 步骤固定，容易提前写清楚 | 需要根据中间结果动态调整 |
| 上下文准备 | 一次就能准备好必要信息 | 很难一次找齐所有相关信息 |
| 成本控制 | 需要严格限制调用次数和资源消耗 | 可以接受多轮调用换取更强的问题解决能力 |
| 模型环境 | 需要使用上下文较小的本地模型 | 可以使用上下文较大的模型，并允许多轮推理 |
| 问题难度 | 输入和输出边界清晰 | 问题复杂，可能需要边做边补充信息 |

可以先记住这组实用判断：

- 对上下文大小有严格要求时，优先考虑 pipeline。
- 需要准确预测或限制 GPU 成本时，优先考虑 pipeline。
- 必须使用上下文较小的本地模型时，优先考虑 pipeline。
- 无法一次准备好全部相关信息时，优先考虑 agent。
- 问题复杂到难以提前写出完整流程时，优先考虑 agent。

在实际项目中，两种方式也经常组合使用。例如，程序先用成本稳定的 pipeline 处理固定步骤，再把真正复杂、需要动态判断的任务交给 agent。

本课程会重点使用 agent 的方式逐步构建 TravelPlanAgent。原因很直观：旅行规划并不是一条固定流水线。用户的目的地、日期、预算、天气和偏好不同，下一步需要查询的信息也会不同。

关于 pipeline 与 agent 的进一步讨论，可以阅读 Sean Goedecke 的文章：[Build agents, not pipelines](https://www.seangoedecke.com/build-agents-not-pipelines/)。

## 小结

这一章先帮你搭了一个底层印象：LLM 会看上下文，然后继续生成内容。

你现在不用把 Transformer、Attention、Token 全部讲得像论文一样严密。先记住几件对后面写 Agent 很有用的事：

- LLM 很擅长组织语言、代码和结构化文本；
- 它不是数据库，也不是搜索引擎，不能默认知道实时或私有信息；
- Token 和上下文窗口会限制模型一次能看见多少东西；
- Prompt、历史对话、工具结果和 RAG 资料，都会变成模型看到的上下文；
- Pipeline 适合固定流程，Agent 则适合让模型参与判断下一步。
