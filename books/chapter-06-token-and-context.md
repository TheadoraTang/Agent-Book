# 第6章 Token 与上下文机制

## 对 TravelPlanAgent 来说意味着什么

上一章我们提到，Agent 需要能够通过多轮交互逐步完成任务。

目前 TravelPlanAgent 每次调用模型时，如果只发送用户最新输入，就会出现一种很尴尬的情况：它每一轮都像第一次见到你。

例如：

```text
用户：我想去杭州玩两天。
Agent：你更喜欢什么类型的行程？
用户：轻松一点，喜欢自然风景。
```

如果第二轮只把“轻松一点，喜欢自然风景”发送给模型，模型并不知道：

- 用户要去杭州；
- 行程是两天；
- 这句话是在回答上一轮问题。

所以，第 6 章对应的实战版本会让 TravelPlanAgent 升级到 v0.4：

```text
支持基于最近 5 轮上下文的连续对话
```


这一章我们先理解两个关键概念：Token 和上下文窗口。然后再看为什么“保留最近 5 轮对话”是一个简单但实用的起点。

---

## 本章目标

读完本章，你应该能理解：

1. Token 是什么，为什么它会影响成本和上下文长度。
2. 上下文窗口是什么，为什么它不是无限大。
3. LLM 的“记忆”和人类记忆有什么区别。
4. 怎样通过 `messages` 保存最近几轮对话。
5. 为什么要裁剪历史消息，以及保留最近 5 轮对话的实现思路。

## Token：模型阅读文本时的基本颗粒

在第 1 章里，我们已经简单提到过 Token。

人读一句话时，习惯按词语和句子理解。LLM 处理文本时，会先把文本切成更小的片段，这些片段就是 Token。

例如：

```text
帮我规划一次杭州旅行
```

模型并不是把它当成一个完整字符串直接理解，而是会先切分成若干 Token，再处理这些 Token 之间的关系。

Token 可能是：

- 一个汉字；
- 一个常见词语；
- 英文单词的一部分；
- 标点符号；
- 数字；
- JSON 里的引号、冒号和括号；
- 代码中的关键字或符号。

不同模型使用的分词方式并不完全一样，所以我们不能简单认为：

```text
1 个汉字 = 1 个 Token
1 个英文单词 = 1 个 Token
```

在教学阶段，不需要手算每句话到底有多少 Token。更重要的是建立一个直觉：

> 输入越长、历史越多、输出越详细，消耗的 Token 通常就越多。

## 一次模型调用会消耗哪些 Token

一次 LLM 调用的 Token，通常不只是用户刚输入的那一句话。

模型真正看到的内容可能包括：

- System Prompt；
- 最近几轮 User 消息；
- 最近几轮 Assistant 回复；
- 工具结果；
- RAG 检索到的知识片段；
- 输出格式说明；
- Few-shot 示例；
- 模型最终生成的回答。

例如一次 TravelPlanAgent 请求可能长这样：

```text
System：你是 TravelPlanAgent，一个旅行规划助手……
User：我想去杭州玩两天。
Assistant：你更喜欢什么类型的行程？
User：轻松一点，喜欢自然风景。
Tool：杭州未来两天可能有阵雨……
User：请根据天气给出调整后的计划。
```

这些内容都会占用 Token。

这也是为什么 Agent 功能越丰富，上下文管理越重要。

## 上下文窗口：模型一次能看到的范围

上下文窗口可以理解为模型这一次调用时能够读取的最大文本范围。

模型并不会永久记住你和它聊过的所有内容。程序需要把必要的历史重新放进 `messages`，模型才能在当前这一次请求中看到它们。

如果历史消息、工具结果和资料太多，超过模型的上下文窗口，就必须裁剪、压缩或筛选。

你可以把上下文窗口想象成一张有限大小的办公桌。

Agent 每次工作时，会把这次任务需要的资料摆在桌面上：

- 工作守则；
- 用户刚才说的话；
- 最近几轮聊天记录；
- 工具返回结果；
- 知识库片段；
- 输出格式要求。

桌面足够大时，一切都很好。

但资料越来越多时，就要做选择：

- 哪些历史对话还重要？
- 哪些工具结果已经过时？
- 哪些知识片段和当前问题无关？
- 是否可以把较早对话总结成一段摘要？

Agent 开发里，上下文管理就是在做这类选择。

## LLM 的“记忆”到底是什么

很多人第一次使用聊天模型时，会觉得模型真的“记住了”前面聊过的内容。

但在最基础的 API 调用里，模型通常不会自动保存历史。

如果程序只发送：

```text
[
  {
    "role": "user",
    "content": "轻松一点，喜欢自然风景。"
  }
]
```

模型只能看到这一句话。

如果程序发送：

```text
[
  {
    "role": "system",
    "content": "你是 TravelPlanAgent，一个旅行规划助手。"
  },
  {
    "role": "user",
    "content": "我想去杭州玩两天。"
  },
  {
    "role": "assistant",
    "content": "你更喜欢什么类型的行程？"
  },
  {
    "role": "user",
    "content": "轻松一点，喜欢自然风景。"
  }
]
```

模型就能理解这句话是在补充杭州两日游需求。

所以，对基础 Agent 来说：

> “记忆”通常不是模型自己永久记住了，而是程序把需要的历史消息重新发送给模型。

## messages 如何维护多轮上下文

一个简单的多轮对话过程，可以用列表保存：

```python
conversation_history = []
```

用户输入后，把 user 消息加入列表：

```python
conversation_history.append(
    {"role": "user", "content": user_input}
)
```

模型回答后，再把 assistant 消息加入列表：

```python
conversation_history.append(
    {"role": "assistant", "content": answer}
)
```

下一轮调用时，把 System Prompt 和历史消息组合起来：

```python
messages = [
    {"role": "system", "content": SYSTEM_PROMPT}
] + conversation_history
```

这样，模型就能看到最近的对话。

在 `TravelPlanAgent_v0.4.py` 中，我们把这个逻辑整理进了一个更清晰的 `ConversationMemory` 类：

<!-- sbs-code -->
```python
class ConversationMemory:
    max_rounds: int = 5
    messages: list[dict[str, str]] = field(default_factory=list)

    def add_user_message(self, content: str) -> None:
        self.messages.append({"role": "user", "content": content})
        self.trim()

    def add_assistant_message(self, content: str) -> None:
        self.messages.append({"role": "assistant", "content": content})
        self.trim()

    def trim(self) -> None:
        max_messages = self.max_rounds * 2
        self.messages = self.messages[-max_messages:]
```

为什么 `max_rounds * 2`？

因为一轮对话通常包含两条消息：

```text
user 消息 + assistant 消息
```

保留最近 5 轮，就大致保留最近 10 条消息。

## 为什么要裁剪历史消息

最简单的做法当然是把所有历史消息全部保存下来。

但随着对话变长，会出现几个问题：

### 1. Token 消耗越来越大

每次请求都把全部历史重新发送，意味着每轮成本都在增长。

### 2. 上下文窗口可能不够

如果消息太多，可能超过模型能处理的最大范围。

### 3. 早期消息可能干扰当前任务

用户一开始问上海旅行，后来改成杭州。如果把大量旧信息全部塞进去，模型可能混淆目的地。

### 4. 工具结果可能过时

天气、票价、营业时间等信息会变化。旧工具结果不应该永久保留。

因此，Agent 需要有上下文策略。

本课程先采用最简单的一种：

```text
只保留最近 5 轮对话
```

它不完美，但很适合初学者理解“历史消息需要主动管理”这件事。

## 常见上下文管理策略

真实项目中，上下文管理有很多做法：

| 策略 | 核心思路 | 适合场景 |
| --- | --- | --- |
| 保留最近 N 轮 | 只留下最近对话 | 入门项目、短任务 |
| 按 Token 裁剪 | 超过长度时删除较早消息 | 不同消息长度差异较大 |
| 对旧消息做摘要 | 把早期对话压缩成短摘要 | 长对话、持续任务 |
| 检索相关记忆 | 只取和当前问题相关的历史 | 长期用户偏好、复杂系统 |
| 区分短期与长期记忆 | 当前任务和用户偏好分开管理 | 更成熟的 Agent |

TravelPlanAgent v0.4 只实现第一种。

后面第 12 章讲 Memory 时，我们会再看更丰富的做法。

## 需要警惕的上下文问题

上下文不是越多越好。

### 问题一：信息污染

如果把无关内容全部放进上下文，模型会更难判断什么最重要。

例如用户正在问杭州行程，但上下文里还塞着大量上海景点资料，回答可能混入错误信息。

### 问题二：过时信息

天气、票价、开放时间等实时信息需要重新查询，不能直接复用旧结果。

### 问题三：Prompt 被淹没

当历史消息特别长时，System Prompt 里的重要规则可能变得不够显眼。

### 问题四：隐私和安全

保存历史消息时，要注意是否包含 API Key、身份证号、联系方式等敏感信息。

入门代码里我们暂时把消息保存在内存中，程序退出后就消失。真实项目如果要保存到数据库，就需要考虑更多安全问题。

## 本章实战：实现最近 5 轮上下文记忆

这一章的实战目标很明确：

```text
让 TravelPlanAgent 支持基于上下文的连续对话
```

和上一版本相比，它新增了：

- `ConversationMemory`
- `add_user_message()`
- `add_assistant_message()`
- `trim()`
- 将最近消息重新组合进 `messages`

你可以尝试这样测试：

```text
你：我想去杭州玩两天。
TravelPlanAgent：你更喜欢什么类型的行程？

你：轻松一点，喜欢自然风景。
TravelPlanAgent：好的，我会按杭州两日轻松自然路线继续规划……
```

然后继续输入更多对话，观察超过 5 轮之后，较早消息会逐步被裁剪。

## 小结

这一章我们理解了 Token 和上下文机制：

- Token 是模型处理文本时的基本颗粒。
- 一次调用里的 System Prompt、历史消息、工具结果、RAG 资料和输出都会消耗 Token。
- 上下文窗口是模型一次能够看到的最大范围。
- 基础 Agent 的“记忆”，通常是程序主动保存并重新发送历史消息。
- 历史消息不能无限增长，需要裁剪、摘要或检索。
- TravelPlanAgent v0.4 先实现最简单实用的策略：保留最近 5 轮对话。

下一章，我们会给 TravelPlanAgent 增加外部工具。

它将不再只依赖模型已有知识，而是能够查询真实天气、读取本地旅行小贴士，并把工具结果带回上下文继续回答。
